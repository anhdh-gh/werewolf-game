# gnhf objective — self-contained, portable across machines

This file is the single source of truth for running `gnhf` (autonomous coding loop,
https://github.com/kunchenguid/gnhf) on this repo. It travels with `git clone` — unlike
`~/gnhf-prompt-*.md` files kept outside a repo on one specific machine, this one is
committed, so a fresh clone on any machine has the full objective and rules immediately.

## New-machine setup

**Automatic (comes free with `git clone`):**
- This file, the whole objective/backlog below.
- `docs/superpowers/specs|plans/*.md`, `_bmad-output/`, the BMAD skills at
  `.claude/skills/bmad-*` (all committed).

**One-time per machine/account — cannot be pushed into the repo, do this yourself:**
1. `npm install -g gnhf` — deliberately NOT a project devDependency: this repo's CI runs
   `npm ci`, which fails hard on any dependency not byte-matched in `package-lock.json`, and
   the lockfile can only be regenerated by actually running `npm install` (unsafe on the
   original PRoot dev machine — see the PRoot note below; fine on a normal machine, but adding
   it there would break CI for anyone still on the constrained machine). A global install
   avoids the tradeoff entirely and takes about the same effort either way.
2. `claude` CLI installed and logged into your own Anthropic account (no way around this,
   nor should there be — never put account credentials in a repo).
3. `vercel login` and `firebase login` — the actual secrets (API keys, service account) live
   in Vercel's cloud env, not on any machine, so logging in is enough to reach them again.
4. A GitHub credential with push access to this repo (`gh auth login`, or a personal access
   token) if you want to verify CI via the REST API instead of the web UI.
5. Optional: `npx uipro init --ai claude` to reinstall the `ui-ux-pro-max` design skill
   locally (deliberately gitignored, see the Design section below for why).

That's the entire list — five quick one-time steps, none of them project-specific busywork.

## How to launch a run

```sh
cat docs/gnhf-objective.md | gnhf --current-branch --push --max-rate-limit-wait 72h \
  --stop-when "<pick the relevant checkpoint from the objective below>"
```

`--current-branch --push` commits straight to `main` and pushes every iteration (matches the
project convention below). If `gnhf` hangs well past a `claude usage limit reached until X`
message it printed (seen happening on real runs — the wait timer occasionally does not fire),
stop it (Ctrl-C once for a graceful stop, waits for the current iteration to commit; twice to
force) and relaunch the identical command — if the reset time has passed, it resumes at once.

## Project rules (apply always, any machine)

1. **Commit straight to `main`.** No feature branches, no PRs for routine work. A `git
   worktree` off `main` is fine for parallel work; just run `npm install` in the main
   checkout, not inside the worktree, if your environment is slow/fragile about it (see the
   PRoot note below — this doesn't apply on a normal fast machine).

2. **Verify via CI + real deploy + live API, not (only) local runs.** After pushing to
   `main`: read the GitHub Actions result (gh CLI or REST API), then check the Vercel/Firebase
   deploy actually went out (`vercel ls`, `vercel logs`, `firebase` CLI), then confirm
   behavior by calling the real live endpoint. This project has twice shipped defects that
   were completely invisible to a green CI (a production-only `ERR_REQUIRE_ESM` module-load
   crash, and RTDB security rules that were correct in the committed file but stale on the
   live database) — CI green is necessary, never sufficient, for anything touching
   infrastructure, auth, or a real external service.

3. **Always free, never paid — chain multiple free providers as fallbacks instead of paying.**
   If free source A runs out (quota, rate limit), fall through to free source B, then C —
   never "pay for more of A" and never "give up because A ran out." Working example already
   in this repo: narration TTS chains Google Cloud TTS / Azure (if the owner ever supplies
   paid keys) down to the free, no-credential `google-translate` provider in
   `scripts/render-narration.mjs` (the same unofficial `translate.google.com/translate_tts`
   endpoint the old `website` branch used live — safe here because it's called once, offline,
   to pre-render static files, not at runtime). Before reporting any feature blocked on
   budget, enumerate every free option — including unofficial/scraped endpoints, weighing ToS
   risk but not ruling them out by default — before telling the owner it needs money.

4. **PRoot/Termux-specific note — only if you're on that kind of constrained environment,
   NOT a universal rule:** the machine this project was originally built on runs inside PRoot,
   where every filesystem syscall goes through ptrace and is extremely slow — a fresh
   `npm install` can take 10+ minutes, and killing one partway through has corrupted
   `node_modules` before (`next` lost its `package.json`, `.bin` went empty). On a normal
   machine, none of this applies: install, build, and test locally as usual, that's strictly
   better (catches problems before push). Only fall back to "push and verify via CI" as the
   *sole* verification method if local runs are genuinely this fragile/slow where you are.

## Design — invoke the skill explicitly, with real references

The `ui-ux-pro-max` skill (deliberately gitignored — see `.gitignore`, reinstall per-machine
with `npx uipro init --ai claude`) auto-activates "when you request UI/UX work" per its own
docs, but verified across dozens of gnhf iterations that auto-activation never actually fires
inside gnhf's scoped technical-task prompts (grepped every iteration log for a real `Skill`
tool_use call against it — zero, ever). **Invoke it explicitly** any time a story touches a
new screen, action UI, or visual component. Skip it for pure backend/rules-only stories.

Owner's own words after looking at the shipped UI: "UI giống sinh viên code quá, xấu kinh
khủng" (looks like a student coded it, extremely ugly) — ground the skill against real named
references for this product category (phone-in-hand social party game, played by a group
physically together):
- **Kahoot** / **Jackbox Games** — bold, high-contrast, big-tap-target UI; strong role/state
  color-coding (dead/wolf/villager instantly visually distinct, not just a text label);
  generous full-screen transitions between phases rather than a plain re-render.
- **Among Us** (mobile) — for role-reveal/action-picker screens: clear big character/role
  iconography, an unmistakable "it's your turn, tap someone" target-picker, satisfying
  color-coded action-confirmation feedback.

Watch for "student project" tells: default Tailwind `bg-blue-500` buttons with no intentional
palette, unstyled default form inputs, inconsistent spacing between visually-similar
components, no defined type scale.

**This is a full-UI-refactor epic, not just new screens going forward** (owner instruction:
"nhớ refactor toàn bộ UI tham khảo UI của các website xịn trên thế giới" — refactor the
ENTIRE existing UI, referencing world-class sites). Audit every already-shipped screen (lobby,
role reveal, night/day phase screens, voting, chat, game-end) against the references above and
bring each up to that bar. Break it into stories per screen/screen-group like every other epic
here (BMAD skills, story docs, tests, live verification) — not one giant undifferentiated
commit. **Sequencing:** owner confirmed 2026-09-08 this comes AFTER the deck-builder and
role-catalog work below finish their current checkpoints — don't jump the queue on your own.

## 1. Room creator picks the exact role deck — replaces the auto-computed formula

**Owner's exact instruction:** "Cho phép chọn nhân vật kèm số lượng nữa. Không để BE tự sinh
số lượng hay phân vai đâu nhé. Người tạo phòng quyết định hết." Do NOT let the backend
auto-generate role counts or the fill order anymore — the room creator decides everything.

**What is NOT changing — the one hard invariant to preserve:** WHO gets WHICH role among the
joined players stays fully random and hidden, exactly as now. This is about the room creator
choosing the DECK COMPOSITION (how many of each role card exist in this game) before dealing —
never let this leak into role-assignment control; that breaks the entire hidden-identity
premise the game depends on.

**What changes:** spec §4.2's current design — `wolfCount = floor((n-1)/4)+1` auto-computed,
"always Seer/Witch/1+ Villager," a fixed fill order, and per-role on/off toggles only — is
superseded. The room creator explicitly sets a count for every available role (0 or more
each) in a deck-builder UI as part of room creation, and `buildRoleList`/`assignRoles` deal
exactly that deck rather than computing one from a formula. This is also the right foundation
for the role-catalog epic below: a formula cannot sensibly decide whether a 10-player game
should include a newly-added role or not — a manual deck-builder is what a large role catalog
actually needs.

**Decided, not open questions — implement exactly these:**
- The deck is composed BEFORE/OUTSIDE the room fills up: the creator sets a target player
  count and the exact role deck for it as part of room CREATION, then the room waits for that
  many people to actually join (not adjusted live as players trickle in). Check the current
  lobby/join/start flow for where this step belongs and how to surface "N of M joined, deck
  already fixed" in the lobby UI (e.g. "3/7 người đã vào").
- Hard constraint: the deck MUST include at least 1 real werewolf-team role (check spec
  §4.1's faction table for which roles count toward this) — server rejects starting a game
  with zero wolf-team roles. Every OTHER old auto-fill requirement is dropped (no more
  "always Seer/Witch/1+ Villager") — full creator control beyond this one guardrail.
- UI shape: a per-role stepper/count-input list in room settings, grouped by faction
  (Sói / Làng / Riêng, spec §4.1's taxonomy), showing a running total against player count.
  Apply the Design section's reference guidance — this screen is exactly what decides whether
  the app feels polished or like a bare CRUD form.
- Existing rooms/games mid-flight when this ships: not a real concern as of the last
  live-preflight check (no long-lived old-format rooms worth migrating) — confirm still true
  rather than assuming.

Treat as its own epic (or the first story of the role-catalog epic's next tier): read the
current `buildRoleList`/`assignRoles` implementation and spec §4.2 fully first, write a proper
story doc via the BMAD skills, implement with full test coverage (including the RTDB rules
implications of a creator-controlled settings write) and live verification.

## 2. Role-catalog epic — expand from 12 roles toward the full Ultimate Werewolf roster

Expand the role roster from the current 12 toward the full Ultimate Werewolf (Bezier Games)
official catalog — well over 100 roles across the base game and expansions (Bonus Roles alone
adds 44; Daybreak, Village, Legacy, Pro Roles, Extreme add more). Genuinely large, multi-epic.

**Owner's explicit process requirements — follow precisely:**
1. Most popular/well-known roles first, obscure ones later — in tiers, not all-or-nothing.
2. Many epics, many stories, many tasks, many subtasks, matching this repo's existing
   plan-doc format (`docs/superpowers/plans/2026-09-06-*.md`, `2026-09-07-*.md`). Use the
   BMAD skills (`bmad-prd`, `bmad-architecture`, `bmad-create-epics-and-stories`, `bmad-spec`,
   `bmad-sprint-planning`) for this — don't invent a different process.
3. Research thoroughly BEFORE planning, plan thoroughly BEFORE implementing: compile a sourced
   role catalog -> write epic/story/task docs -> implement in the tiers the plan lays out.

**Why 12 -> 100+:** the owner asked "does the game have ALL the roles in the world" and
pushed back on 12. The current 12-role scope was a deliberate v1 decision (spec §4.1-4.2) —
superseded for roster SIZE only; nothing else about the spec's architecture, invariants, or
the 12 already-shipped roles (Werewolf, Traitor, Seer, Bodyguard, Witch, Hunter, Cupid, Muter,
Cursed, Lycan, Villager, Tanner) is thrown out. This is an expansion, not a rewrite.

**Canonical source, clarified with the owner: Ultimate Werewolf (Bezier Games) specifically**
— not homebrew/community roles, not "every werewolf variant on the internet." If a role's
exact ability text can't be found from an Ultimate Werewolf source, don't invent one from a
same-named role in a different game (Werewolves of Miller's Hollow, One Night Ultimate
Werewolf, random apps) — flag "name known, exact wording not found" and move on.

**Task 1 (first, before any planning doc): compile the sourced role catalog.** No single
clean web source enumerating all 100+ roles was found in earlier research — search engines
return partial lists and general counts, not the full roster in one place. Leads worth
checking: BoardGameGeek file "Ultimate Werewolf Role list for all versions" (filepage id
99038 — likely a download, not a plain-fetchable page); board-games.fandom.com/wiki/
Ultimate_Werewolf/Roles (returned HTTP 402 once, may be transient); beziergames.com's own
per-expansion product pages (most authoritative when reachable). "One Night Ultimate
Werewolf" roles (Alpha Wolf, Mystic Wolf, Dream Wolf, Sentinel, Apprentice Seer, Paranormal
Investigator, Witch, Village Idiot, Revealer, Curator, Bodyguard from its Daybreak expansion)
are a DIFFERENT sub-line — single-night, no repeating day/night loop, no fit with this
project's phase engine as-is — flag any One Night-only role as needing real adaptation design
or documented exclusion, don't assume it drops in.

Output: a checked-in document (e.g. `_bmad-output/planning-artifacts/werewolf-role-catalog.md`
or this repo's existing convention for research artifacts) listing every role found with:
exact source (product/expansion, URL), team (village/werewolf/third-party, spec §4.1's
taxonomy), plain-language ability summary, and a popularity tier. Cite sources inline — every
later epic/story is written against this; an uncited or guessed entry poisons everything
downstream.

**Then: planning docs via BMAD skills.** One epic per popularity tier (or sensible batch
within a large tier) — not one epic for "the roles project," not one per individual role.
Each story = one role or a tightly related small group, at the granularity this repo's
existing plan docs already use. Each story needs: the cited real ability; how it maps onto
the existing phase engine (`docs/superpowers/plans/2026-09-07-game-engine.md`) — new phase or
fits an existing one; how `requiredActorsForPhase()`-style logic and RTDB `actions/` rules
extend (see the security-hole fix in `2026-09-07-resilience.md`'s closing section for the
exact pattern new action-phase rules must follow); natural Vietnamese UI text matching
`src/lib/game/labels.ts`/`narration.ts`'s existing tone; test coverage (unit + this repo's
e2e-suite pattern + RTDB rules tests).

**Then: implement tier by tier — spans many future gnhf runs.** Don't attempt all tiers in
one run. A tier's stories, merged with passing CI and live verification, is a complete,
reportable unit on its own. Track status per role (`planned`/`in progress`/`done`) in the
catalog doc or whatever tracking convention exists, so progress is visible without
re-deriving it.

**If the epic looks like it will never realistically "finish"** (100+ roles is enormous), say
so plainly once a real tier structure exists and let the owner decide an earlier stopping
point — don't silently grind forever, and don't independently decide to skip to the
full-UI-refactor or English epics on your own reasoning either.

**Hard rule throughout this epic:** Vietnamese is the UI language for every role added here

## 3. Small bounded tasks — tiny, can slot in anytime, don't block on them

**PWA install-prompt coverage across browsers.** `src/components/InstallPrompt.tsx` only
handles iOS (manual hint) and "wait for `beforeinstallprompt`" (silently shows nothing if
that Chromium-only event never fires — e.g. on Firefox for Android, which never fires it).
Fix as 3 buckets, not a per-browser list:
1. Chromium family (Chrome, Samsung Internet, Edge, Brave, Opera, Vivaldi, Yandex, Cốc Cốc,
   Huawei Browser, QQ Browser, Naver Whale, any derivative) — already correctly handled by
   the existing branch; verify a couple for real rather than assuming, don't rewrite it.
2. Firefox for Android — needs its own manual-hint branch (mirror the iOS one — verify
   Firefox's actual current menu wording for "add to home screen").
3. Generic timeout fallback for everything else: if not iOS, not detected-Firefox, and
   `beforeinstallprompt` hasn't fired after ~3s, show a generic hint ("Tìm 'Thêm vào Màn
   hình chính' trong menu trình duyệt"). Automatically covers Opera Mini (known very limited
   PWA support — verify rather than assume), Mi Browser on China-domestic Xiaomi devices
   (GMS-less ROM — no documentation found either way, test if a device is available), and any
   untested/future browser without special-casing each by name.

Keep to these 3 branches. Add tests for the timeout-fallback and Firefox-detection paths.

**Per-device narration mute toggle.** Same-table games can have every phone play the shared
narration (`useNarrationPlayback`) simultaneously — no cross-device sync exists, so phones
close together can produce an audible echo. `useTurnChime` (private "it's your turn" alert)
is a separate mechanism, not part of this — don't touch it. Fix: a small per-device mute
toggle for narration playback only, backed by `localStorage` (personal preference, not synced
game state). Default ON (current behavior). UI: small icon near existing narration UI
(check `GameScreen`/wherever `useNarrationPlayback` is wired). A muted phone stays exactly
where its owner left it (face-down in front of them, as already designed) — no "designated
speaker phone in the middle of the table" concept; whoever's phone stays unmuted uses it
normally, including tapping it on their own turn like anyone else. Add a test for the mute
flag gating playback.
